# Flutter 项目开发规约（路由与架构篇）

本文档定义项目在路由、分层架构、状态管理和代码审查上的统一标准。默认技术栈为 Flutter + GoRouter + Provider + ChangeNotifier。

## 零、开发前必读

- 每次开始开发前，开发者和 AI 助手都必须先阅读本文档，确认当前任务涉及的路由、架构、国际化、布局和测试规则。
- 开始实现前必须先查看相关既有代码、路由配置、本地化资源和原型资料，不得只凭记忆或假设改动。
- 若需求与本文档冲突，必须先更新规约或明确记录例外原因，再实现代码。
- `dart run scripts/check_project_rules.dart` 会在每次运行时提示本文档入口，并校验本节和多屏幕布局规则没有被删除。

## 一、基础依赖与入口

### 1.1 必备依赖

项目若启用本文档规约，`pubspec.yaml` 必须包含：

```yaml
dependencies:
  flutter_localizations:
    sdk: flutter
  go_router: ^16.0.0
  intl: ^0.20.0
  provider: ^6.0.0
```

版本号可随项目升级调整，但不得在未同步修改规约和迁移方案的情况下替换核心路由或状态管理方案。

### 1.2 应用入口

- `lib/main.dart` 只负责启动应用、初始化必要服务和注入顶层依赖。
- `lib/app.dart` 负责创建 `MaterialApp.router`，并接入 GoRouter。
- 禁止在入口层放置业务页面、示例 Counter 逻辑或临时调试 UI。

推荐结构：

```text
lib/
├── main.dart                 # runApp、顶层依赖初始化
├── app.dart                  # MaterialApp.router 与主题配置
├── routing/
│   ├── app_router.dart       # GoRouter 实例
│   └── app_routes.dart       # 路由常量
├── features/
├── shared/
└── core/
```

## 二、路由管理规约（基于 GoRouter）

### 2.1 统一入口与配置

- 强制使用 GoRouter 管理页面路由。业务代码禁止直接使用 `Navigator.push`、`Navigator.popAndPushNamed` 等命令式跳转 API。
- 允许在 GoRouter 不覆盖的底层场景使用 `Navigator`，例如系统返回拦截、嵌套 `Navigator` 组件或第三方组件内部导航；使用前必须在代码注释中说明原因。
- 所有路由路径必须定义在 `AppRoutes` 等常量类中，禁止在业务代码中硬编码路径字符串。
- 路径使用小写斜杠法，例如 `/settings/privacy`。
- 路径参数使用驼峰命名，例如 `/user/:userId`。
- 页面跳转优先使用命名路由，减少字符串拼接。

### 2.2 导航行为

- 普通页面进入使用 `context.push(...)`，保留返回栈。
- 根级跳转使用 `context.go(...)`，用于登录后进入主页、退出登录回到登录页、底部导航栏根页面切换等场景。
- 返回上一页使用 `context.pop(...)`；需要返回结果时，调用方必须处理 `Future` 的空值或取消场景。
- 底部导航栏、侧边栏等多入口页面切换不得反复 `push` 同级根页面。

### 2.3 参数传递

- 可恢复页面优先通过路径参数或 query 参数传递稳定标识，例如 `/users/:userId` 或 `/search?keyword=cat`。
- 页面需要的数据由 ViewModel 根据参数加载，不应把完整业务对象当作页面状态来源。
- `extra` 只用于不可深链、不可刷新恢复的临时上下文，例如刚创建成功后的短期展示数据。
- 使用 `extra` 时，Route builder 必须做类型检查、空安全处理和降级跳转。
- Web 或需要深链恢复的页面不得依赖未序列化的 `extra` 对象作为唯一数据来源。

### 2.4 Shell 路由与多 Tab 子栈

- 只有一个公共外壳且不需要每个 Tab 保留独立返回栈时，可以使用 `ShellRoute`。
- 底部导航栏、侧边栏工作台等多 Tab 页面，若每个 Tab 需要保留独立导航栈，必须使用 `StatefulShellRoute.indexedStack` 与 `StatefulShellBranch`。
- 每个 branch 应有独立的 `NavigatorKey`，并在切换 Tab 时保留对应子栈状态。

### 2.5 路由守卫

- 登录态、首次启动、权限不足等全局重定向必须在 GoRouter 的 `redirect` 中统一处理。
- 禁止在 Widget 的 `initState` 中执行页面级登录拦截或强制跳转。
- `redirect` 逻辑必须避免循环重定向，并明确列出不需要登录的白名单路由。

## 三、架构分层规约（MVVM 风格）

### 3.1 目录结构

项目 `lib/` 下按照功能模块组织：

```text
lib/
├── app.dart
├── main.dart
├── routing/
│   ├── app_router.dart
│   └── app_routes.dart
├── core/                     # 跨业务基础设施
│   ├── errors/
│   ├── network/
│   └── utils/
├── shared/                   # 通用 UI、服务和扩展
│   ├── services/
│   ├── widgets/
│   └── extensions/
└── features/
    └── feature_name/
        ├── data/             # Model、DTO、Repository、Service
        ├── viewmodel/        # ViewModel、Command、UI State
        └── view/             # Page、Widget
```

模块内文件命名使用小写下划线，例如 `profile_view_model.dart`、`profile_page.dart`。

### 3.1.1 单一职责与文件边界

- 单个页面和可复用组件必须单独一个文件，页面文件不得顺手承载其他页面、跨页面组件或无关业务模块。
- 每个 `*_page.dart` / `*_screen.dart` 文件只定义当前页面及只被当前页面使用的私有小组件；一旦组件被两个及以上页面复用，必须移动到独立组件文件。
- 底部导航、原型画布、通用卡片、搜索框、按钮、状态标签等跨页面 UI 组件，应放在 `shared/widgets/` 或当前 feature 的独立组件文件中，不得隐藏在某个页面文件里。
- 路由中引用的页面类必须来自对应页面文件，例如 `agent_page.dart` 只暴露 `AgentPage`，不得从 `home_page.dart` 暴露 Agent、知识库或设置页面。
- 页面文件过长或出现多个业务区域时，应优先拆分为局部组件文件，避免单个文件同时承担页面、导航、组件库和业务展示职责。

### 3.2 View 层

- View 负责渲染 UI、接收用户输入、调用 ViewModel 方法。
- View 禁止直接调用 API、数据库、Repository 或 Service。
- View 禁止承载业务规则，例如权限判断、价格计算、状态流转、数据合并。
- View 允许存在纯展示逻辑，例如加载态/空态/错误态分支、布局判断、简单空安全兜底和组件组合。
- 页面动态数据必须来自 ViewModel 或其暴露的 UI State，不得在 Widget 中复制一份业务状态长期缓存。
- 用户事件通过 `context.read<MyViewModel>().method()` 或 `Consumer` 回调传递给 ViewModel。

### 3.3 ViewModel 层

- ViewModel 默认继承 `ChangeNotifier`。
- ViewModel 持有页面 UI State，并负责把 Model/DTO 转换为 View 可直接使用的数据。
- ViewModel 调用 Repository 或 Service 完成数据读取、提交和业务流程编排。
- 只有影响 UI 的状态变化才调用 `notifyListeners()`。
- ViewModel 不得持有 `BuildContext`，不得 import `flutter/material.dart` 或依赖 Widget。
- ViewModel 允许 import `package:flutter/foundation.dart` 使用 `ChangeNotifier`、`ValueNotifier` 等基础能力。
- 异步操作应统一暴露 `isLoading`、`errorMessage`、`canSubmit` 等状态，避免 Widget 内重复写 `try-catch`。
- 复杂异步命令可以封装为 `Command` 对象，供按钮、表单和列表刷新复用。

### 3.4 Service / Repository 层

- Service 和 Repository 必须是纯 Dart 业务对象，不包含 UI 逻辑。
- Repository 负责屏蔽数据来源差异，例如远程 API、本地缓存、数据库。
- Service 负责单一能力，例如 HTTP、认证、文件、定位、WebSocket。
- 若 Service 需要主动推送数据，必须暴露 `Stream<T>`。
- ViewModel 可以订阅 Service 的 Stream，并在收到数据后更新状态。
- Service 禁止持有 ViewModel 引用，禁止直接调用 `notifyListeners()`。

## 四、单向数据流

应用逻辑遵循以下闭环：

1. View 捕获用户操作。
2. View 调用 ViewModel 方法。
3. ViewModel 调用 Repository 或 Service 获取数据、执行业务流程。
4. ViewModel 更新 UI State。
5. View 根据新状态重建 UI。

禁止反向依赖：

- Service -> ViewModel：Service 不持有 ViewModel。
- View -> Service：Widget 不直接调用 Service。
- ViewModel -> View：ViewModel 不调用 Widget 方法，不持有 `BuildContext`。

## 五、依赖注入与状态管理

### 5.1 DI 选择

- 默认使用 `provider` 进行依赖注入和 `ChangeNotifier` 状态管理。
- 跨页面共享的 Service 在应用顶层通过 `Provider` 注入。
- 页面级 ViewModel 在对应路由页面内创建，随页面销毁自动释放。
- 如项目需要迁移到 Riverpod，必须先提交迁移方案，说明 Provider 与 Riverpod 的共存边界和迁移顺序。

### 5.2 ViewModel 生命周期

- 页面级 ViewModel 的作用域应与页面生命周期一致。
- Tab 根页面的 ViewModel 若需要保留状态，应挂在对应 branch 或 shell 的稳定作用域中。
- 全局状态只允许放置真正跨模块共享的状态，例如认证态、用户基础信息、应用配置。
- ViewModel 中订阅的 Stream、Timer、Controller 必须在 `dispose()` 中释放。

### 5.3 `setState` 使用边界

- 业务状态、页面数据状态、加载状态和错误状态必须进入 ViewModel。
- 纯局部 UI 状态可以使用 `setState`，例如展开/收起、临时动画状态、焦点展示、局部 hover、高亮。
- 一旦局部状态影响业务流程、跨组件共享或需要测试，应上移到 ViewModel。

## 六、国际化规约

### 6.1 基础方案

- 项目统一使用 Flutter 官方 `gen_l10n` 方案生成本地化代码。
- 本地化资源统一放在 `lib/l10n/` 目录，文件使用 ARB 格式。
- 默认语言文件命名为 `app_zh.arb` 或项目确定的默认语言；其他语言按 locale 命名，例如 `app_en.arb`、`app_zh_Hant.arb`。
- `l10n.yaml` 必须放在项目根目录，并明确配置 `arb-dir`、`template-arb-file`、`output-localization-file`。
- `MaterialApp.router` 必须配置 `localizationsDelegates`、`supportedLocales` 和 `locale` 或系统 locale 跟随策略。

推荐结构：

```text
lib/
└── l10n/
    ├── app_zh.arb
    ├── app_en.arb
    └── app_zh_Hant.arb
l10n.yaml
```

### 6.2 文案使用

- 所有面向用户展示的文案必须来自本地化资源，禁止在 Widget、ViewModel、Service 中硬编码用户可见字符串。
- 允许硬编码的字符串仅限日志、调试标记、路由路径、语义稳定的协议字段和测试专用数据。
- View 层通过 `AppLocalizations.of(context)` 或项目封装的 `context.l10n` 获取文案。
- ViewModel 不得持有 `BuildContext`，因此不得直接读取 `AppLocalizations`。
- ViewModel 需要展示文案时，应暴露状态码、枚举或错误类型，由 View 层映射为本地化文案。

### 6.3 Key 命名与维护

- ARB key 使用 lowerCamelCase，例如 `profileEditTitle`、`loginInvalidPassword`。
- Key 名称描述语义，不描述页面位置或视觉样式；避免 `button1`、`titleText` 等不稳定命名。
- 删除页面或功能时，必须同步清理不再使用的本地化 key。
- 新增默认语言 key 时，必须同步补齐所有已支持语言；短期缺失必须在 PR 中说明原因和补齐时间。
- 不得在代码中拼接本地化 key 后动态取值，避免静态检查失效。

### 6.4 参数、复数与选择

- 带变量的文案必须使用 ARB placeholder，例如用户名、数量、金额、时间。
- 不得用字符串拼接生成句子，例如 `'Hello ' + name`。
- 数量相关文案必须使用 ICU plural，避免英文单复数和其他语言复数规则错误。
- 性别、状态、类型等分支文案优先使用 ICU select，而不是在代码里写多套 `if-else` 文案。
- Placeholder 必须声明类型、示例值和必要描述，便于翻译和审查。

### 6.5 日期、数字、金额与单位

- 日期、时间、数字、百分比和金额必须使用 `intl` 或项目统一格式化工具按 locale 格式化。
- 禁止手写固定格式给用户展示，例如 `yyyy-MM-dd HH:mm`、`$price 元`。
- 单位文案需要进入本地化资源，不得与数值直接拼接。
- 后端返回的错误码、状态码不得直接展示给用户，必须映射为本地化文案。

### 6.6 布局与可访问性

- UI 必须预留文案长度变化空间，英文、繁体中文和其他目标语言不得发生截断或重叠。
- 按钮、Tab、列表项等固定空间组件必须测试长文案场景。
- 若支持阿拉伯语、希伯来语等 RTL 语言，布局必须验证 `Directionality`、图标方向和滑动手势。
- `semanticsLabel`、`tooltip`、空态、错误态、权限提示等辅助文案同样必须国际化。

### 6.7 审查要求

- 新增用户可见文案时，PR 必须同时包含 ARB 变更。
- 修改文案 key 时，必须同步更新所有引用和所有语言文件。
- 国际化生成文件不得手工修改。
- PR 检查中必须关注是否存在新增硬编码用户文案、字符串拼接句子、未本地化错误提示和未格式化日期数字。

## 七、UI 布局与多屏幕适配

- 多屏幕尺寸适配必须优先使用浮动布局，不得只按单一设备写死绝对尺寸。
- 从 Pencil、Figma 等原型实现页面时，应以原型尺寸作为基准画布，使用 `Stack` / `Positioned` / `LayoutBuilder` / `Transform.scale` 等方式按屏幕宽高比例进行整体缩放或分区缩放，确保视觉比例、间距、底部导航和关键控件在不同屏幕上保持一致。
- 使用浮动布局时必须明确基准尺寸，例如设计稿宽高、安全区高度和底部导航高度，并把这些数值集中定义为常量，避免散落在组件内部。
- 固定格式页面、工作台、仪表盘、绘图/编辑器、移动端原型还原页，优先采用原型坐标映射的浮动布局；普通表单、列表、设置页可使用自适应流式布局，但必须验证小屏和大屏不会截断、重叠或错位。
- 禁止为了适配某一台设备反复堆叠 `SizedBox`、魔法间距或只依赖 `SingleChildScrollView` 掩盖布局问题。
- 底部导航、工具栏、状态卡、固定面板等关键区域必须在不同屏幕高度下保持可达；如空间不足，应按比例缩放或设计明确的滚动/折叠策略。
- 页面实现完成后至少通过一组小屏和一组常规屏尺寸检查布局，不得出现文字溢出、控件重叠、底部导航遮挡正文或安全区冲突。

## 八、错误处理与可测试性

- Repository / Service 层不得把底层异常直接泄漏给 View。
- ViewModel 应把异常转换为 UI 可展示的错误状态或明确的失败结果。
- ViewModel 必须能够用纯 Dart 单元测试覆盖核心状态流转。
- 路由参数解析、权限重定向、表单提交、列表加载等高风险逻辑必须有测试。
- 新增功能至少覆盖 ViewModel 的成功、失败和边界状态。

## 九、代码审查检查清单

Pull Request 必须按以下清单核查：

- 是否新增了 `Navigator.push` 或硬编码路由字符串？
- 多 Tab 页面是否使用了合适的 `StatefulShellRoute` / `ShellRoute`？
- 页面是否依赖 `extra` 承载可恢复业务状态？
- 页面文件是否只包含当前页面职责，可复用组件是否已拆到独立文件？
- Widget 是否直接调用了 Service、Repository、API 或数据库？
- Widget 中的条件判断是否只是展示逻辑，而不是业务规则？
- ViewModel 是否 import 了 `flutter/material.dart`、持有 `BuildContext` 或调用 Widget？
- 业务状态是否绕过 ViewModel 使用了 `setState`？
- Stream、Timer、Controller 是否正确释放？
- Service / Repository 是否只处理数据和能力，不包含 UI 状态？
- 新增用户可见文案是否进入 ARB，并补齐所有支持语言？
- 日期、数字、金额、单位和复数文案是否按 locale 格式化？
- ViewModel 是否只暴露错误类型或状态码，而不是直接持有本地化文案？
- 多屏幕页面是否采用浮动布局或经过明确论证的自适应布局？
- 原型还原页面是否按设计稿基准尺寸进行比例缩放，并验证小屏/常规屏？
- 新增 ViewModel、路由守卫或关键数据流是否有测试覆盖？
